# External Technical Review — Summary and Response

**Context:** Following project completion, an independent technical evaluation was commissioned to assess the pipeline from the perspective of a BCI/ML engineering hiring review. This document summarizes the review's key findings and provides a point-by-point response — accepted, disputed, or deferred, with reasoning — consistent with the engineering standard held throughout this project: report findings honestly, explain reasoning, and state plainly what remains unresolved. The original review document is retained by the author; this page synthesizes its substantive technical content rather than reproducing it verbatim.

## Overall Assessment (as reviewed)

The review characterized the completed project as a **strong research-engineering prototype**, appropriate as a positive hiring signal for a junior-to-mid BCI software/ML engineering role, while explicitly distinguishing it from a production-grade or commercial neurotechnology system. It noted the project's genuine strengths — a fully working, debugged real-time pipeline; an honestly-quantified and explained real-time/offline accuracy gap; a working multi-page monitoring application; and a demonstrated capacity for methodical, evidence-based debugging (e.g., the trial-scoring-window and filter-edge-distortion fixes) — alongside a specific, technically substantive list of gaps.

## Findings and Response

| # | Finding | Response | Reasoning |
|---|---|---|---|
| 1 | Validation methodology permitted test-set leakage: checkpoint selection and final reporting used the same held-out session. | **Accepted and fixed.** | Confirmed as a genuine bug in the original training loop, not a defensible design choice. Corrected via a strict three-way split and full-data refit (see `docs/decisions.md`, D-013). All reported numbers, ONNX exports, and the live-demo subject selection were regenerated against the corrected methodology. |
| 2 | Real-time filtering (`filtfilt`) is non-causal and not standard practice for production real-time BCI systems. | **Accepted; fix scoped, not yet implemented.** | The specific, correct alternative (causal `sosfilt` with persistent filter state) is identified in the README's Engineering Roadmap. Deferred deliberately given a fixed timeline for portfolio completion — see `docs/decisions.md`, D-014, for the explicit reasoning distinguishing this from item 1. |
| 3 | No classical baseline (CSP/Riemannian geometry) exists to contextualize whether EEGNet's accuracy reflects a genuine advantage over simpler, non-deep-learning methods on this dataset. | **Accepted; listed as roadmap item.** | A fair and correct gap. Deep-learning accuracy without a classical baseline for comparison is a known weakness in applied ML work generally, not specific to this project, but worth closing. |
| 4 | No cross-subject generalization strategy or leave-one-subject-out (LOSO) evaluation; each model is trained and evaluated on one person's own data only. | **Accepted; listed as roadmap item.** | Consistent with this project's own findings on subject-to-subject variability (see Results): a LOSO evaluation would quantify, rather than assume, how much pooling data across subjects helps or hurts, which is directly relevant to any real deployment scenario involving a new user. |
| 5 | No configuration-management layer; filter parameters, buffer margins, and the validated scoring interval live as source-code constants rather than an external, environment-overridable config. | **Accepted; listed as roadmap item.** | Correct, standard production-readiness gap. The current approach (a single shared constants module, `src/common/bci_utils.py`) was itself a deliberate improvement over earlier per-file duplication (see `docs/decisions.md`, D-011) but stops short of true config management. |
| 6 | Debugging/verification scripts (`sanity_check_*.py`, etc.) live alongside production code in `src/`, rather than in a dedicated `tests/` directory with automated assertions. | **Accepted; listed as roadmap item.** | Accurate. These scripts were genuinely useful and load-bearing during development (see `docs/PROJECT_NARRATIVE.md`, Phase 5) but were never converted into a maintained, automated regression suite. |
| 7 | The reported inference latency benchmark (0.29ms, ONNX Runtime CPU) could be misread as total system decision latency, when it is model-compute latency only. | **Accepted; README updated.** | A fair clarity critique, not a technical error — the benchmark itself was correctly measured and described in context at the time, but the README's Results section has been revised to state explicitly that compute latency is not the dominant term in total system latency (the ~4-second window-fill requirement is). |
| 8 | Recommended adding a README section explaining the reasoning behind key architectural choices (why EEGNet, why this filter band, why subject-specific models), not just describing what was built. | **Accepted.** | Directly implemented as `docs/decisions.md`, structured as a dated, reasoned decision log rather than a single README subsection, since the number and depth of decisions warranted a dedicated document. |
| 9 | BCI illiteracy (subjects performing near chance) was identified and correctly attributed to a known literature phenomenon, but the underlying cause was not further investigated. | **Acknowledged; not disputed, not immediately actionable.** | Correct as stated. Retained explicitly in the README's Limitations section rather than the Roadmap, since investigating the root cause (signal quality, electrode-level factors, individual strategy differences) is a genuinely open research question rather than a scoped engineering task with a known fix. |

## Closing Note

Item 1 (validation leakage) was treated differently from every other finding in this table: it was the only one that made a previously reported number actually incorrect, rather than representing an accepted design tradeoff or a legitimate scope boundary. It was fixed in full — not selectively, and not by retaining whichever of several retraining runs happened to produce the most favorable number, a shortcut that was considered and explicitly rejected as reproducing the same leakage mechanism it was meant to fix (see `docs/decisions.md`, D-013). Every other finding in this table is addressed either through direct action taken (items 6/7/8 partially, 9) or through an honestly scoped and reasoned deferral (items 2–6), consistent with the standard held throughout this project's development: measure honestly, explain reasoning, and state plainly what remains unresolved.
